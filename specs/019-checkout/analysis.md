# Analysis and review record: checkout

Written and built by Claude Code (lead). Codex (gpt-6.1-sol, read-only) reviewed as a second opinion. Every finding
was checked against WooCommerce 11.1.0's source before it was applied, and each fix has a t60 check that fails when the
fix is removed (`evidence/mutation.txt`), unless the record says why it cannot have one.

| Round | Verdict | Findings, and what was done |
|---|---|---|
| 1 | FIX FIRST | Four High, five Medium. Pay-for-order and payment callbacks bypassed the placement hooks: pay-for-order reserves before the gateway charges, and an order reaching a paid status without a reservation is reserved then, or marked for staff with a note when refused (a payment already taken cannot be refused). A failed order released, then retried, was taken as reserved; a reserve the source applied but never answered was asked again under a new key; an order edited after placement released its new quantity: the order keeps a reservation record per line (stock, quantity, key generation, state), a retry re-sends an unanswered reserve's key, a line undone or released asks with new keys, and releases use the record. A retried checkout was refused for the visitor's own reservation: it counts as theirs at the cart check. Trashing or deleting an unpaid order left its stock held: released first. A refused classic placement kept its coupons held: released. The district was required for every country: for an Egyptian address only. The HTTP refusal test could pass with the reservation hook removed: the hook is now checked with a source that answers stock but refuses the change |
| 2 | FIX FIRST | Four High, four Medium. Fixed: an order edited after reserving was taken as reserved: it counts only when its record matches its lines, and reserving again resizes a changed line by the difference (or gives back a line removed or swapped); a retried checkout whose stock its own order already holds was still refused: it passes; an existing order paid through the Store API skipped the district: it is checked before any Store API payment. Recorded as limits, not built here, because they depend on how the ERP holds a reservation (PRE-09): an undo or a release the source never answered, and a reserve left unsure when the order is then cancelled, are marked for reconciliation, not retried; a crash between a source's change and the saving of the record is not journalled; a paid order the source refuses is marked for staff, and fulfilling it is not blocked |
| 3 | FIX FIRST | Two High, one Medium, all fixed. A quantity changed 1, 3, 1, 3 reused the resize key, so the second rise took nothing: each resize is numbered per line and written to the record before it is sent. A crash after an undo reached the source, before the record was saved, left the line to be taken as reserved under its old key: the undo is written (undoing) before it is sent, and sent again first by the next placement or release. Paying an existing order through the Store API dropped the district it was sent: it is kept on the order before the check. t60 simulates the crash on both sides of the undo |
| 4 | FIX FIRST | Two High, both fixed. A crash after a release reached the source left the line reserved, so paying again took nothing: the release is written (releasing) before it is sent, and sent again first. A resize applied but unanswered, with the order changed back, counted as reserved: a pending resize is no reservation |
| 5 | FIX FIRST | Two High, both fixed. A crash after a reserve reached the source, then the line edited, re-sent its key with the new quantity: the reserve is written (reserving) with its quantity before it is sent, and settled as sent first; an order released with a reserve unanswered now asks it again and gives it back. Two payments of one order at once worked from one stale record, so the failing one undid the other's reservation: reserve and release run under a per-order lock, with the record read again inside it |
| 6 | FIX FIRST | Two High, both fixed. Inside the lock the lines could still come from the caller's stale copy: all reservation work runs on the order loaded again inside the lock. The paid-status handler trusted its copy's reservation outside the lock, and a failure's release did not check the order was still failed: both are decided inside the lock from the stored status; a paid order whose lock cannot be taken is marked for staff |
| 7 | FIX FIRST | One High, fixed. The copy loaded inside the lock could still come from this request's caches (the order object, its item list, each item and its meta): they are dropped for the order before it is loaded. t60 stores a new quantity straight to the database, as another request would, while this one holds the old one in its caches |
| 8 | READY | No High or Medium findings outside the recorded PRE-09 limits |

Known limits, recorded in the specification, each for the ERP's reservation mechanism (PRE-09) to settle: an undo or a
release the source does not answer is marked unsettled; a paid order the source refuses is marked for staff rather than refused, and fulfilling it is not blocked.
