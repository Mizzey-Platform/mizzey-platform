# Analysis and review record: accounts

Written and built by Claude Code (lead). Codex (gpt-6.1-sol, read-only) reviewed as a second opinion. Every finding
was checked against WooCommerce 11.1.0's, WordPress's and CoreX's source before it was applied, and each fix has a t58
check that fails when the fix is removed (`evidence/mutation.txt`).

| Round | Verdict | Findings, and what was done |
|---|---|---|
| 1 | FIX FIRST | One High, seven Medium, one Low. CoreX's lockout counted each spelling of a mobile number separately: the number now becomes its account's username before the lockout sees it. Two requests could both redeem one link: the link is spent by one delete only one request can win. Opening a link signed the browser in at once (a link sent by someone else, or opened by a mail scanner): the account page now asks to confirm, by a form tied to the visitor's own session, and a visitor signed in elsewhere is not switched. A username spelled like a number could win over the number's holder, and uniqueness was checked only at registration: a claim registry, one insert per number, kept in step with every write of the billing phone, and no generated username spelled like a number. A link stayed valid after a password or email change: it is bound to both. The shared limit test now alternates real password resets with links. Timing and the number check at registration were kept that round, and reopened in round 2 |
| 2 | FIX FIRST | Five Medium. A delayed release could delete another account's new claim: the delete names the owner. A number could be resolved twice in one sign-in: once. Numbers saved before claims existed were unclaimed: claimed once, none for a number several accounts hold. Registration said whether a number belonged to a customer: it no longer refuses one, and the new account keeps it for delivery without signing in with it; an unknown number costs the same password work at sign-in. The link request answered after its work, so its time said whether an email had a customer account: the work runs after the answer is sent where PHP runs under FPM (to be confirmed on staging); on a development runtime without FPM it still runs within the request |
| Own test runs | One defect, one guard | A claim whose owner no longer holds its number could never be taken: it is taken over by one update naming the stale owner. Deleting an account already released its number (WordPress fires `deleted_user_meta` for the billing phone as it deletes the account's meta); the release now also runs on `delete_user`, before any meta is deleted, so it does not depend on the order of the meta rows. Found when a second t58 run met the accounts an interrupted run had left holding the same fixed numbers; t58 now uses numbers of its own run. The same run showed a test helper casting a failed `wp_insert_user()` to the id 1, which deleted the development runtime's first administrator: the test bootstrap now never deletes user 1, and t58 makes its users safely |
| 3 | FIX FIRST | Five Medium. A claim being completed could look abandoned and be taken over: staleness is read from the owner's saved billing phone, which is written before the claim. Overlapping writes to one account's phone could leave its claim on the earlier number: the claim follows only the value saved after it. A number several older accounts shared could be claimed later by a third: it is reserved for none. Two were recorded, not fixed: phone sign-in without a one-time code can always be used to test whether a number is held (register with it, then try it), which only ownership proof would end, and that is SMS, P2 (INT-07); the link request's equal timing needs PHP-FPM |
| 4 | FIX FIRST | Two Medium. Overlapping changes of one account's phone, and a takeover racing a reclaim, could leave a claim on the wrong number: a number's claim and an account's phone change now take turns under MySQL named locks, the account's saved phone is read under the lock, and holder() also requires the owner's saved phone to be the number, so a binding that loses a race signs in to nobody |
| 5 | FIX FIRST | One Medium. The backfill published claims outside the account's lock: it now goes through the same locked path |
| 6 | FIX FIRST | One Medium. Two first requests for a link at once could store two token rows: the link is stored as the account's one row, replaced under a lock per account |

Known limits, recorded in the specification: the link request's timing is equal only where PHP-FPM sends the answer
first; WooCommerce's own registration form says whether an email already has an account (native, AUTH-01); without a
one-time code, phone sign-in can be used to test whether a number is held (AUTH-02's reduced scope).
