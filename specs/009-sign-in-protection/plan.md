# Implementation Plan: sign-in protection, automated account creation and sessions

**Branch**: `009-sign-in-protection` | **Date**: 2026-10-30 | **Spec**: [spec.md](spec.md)

## Summary

CoreX's login protection, off by default, provides the limit and the lockout; a Developer command turns it on once with
the documented settings, keeping WordPress's default sign-in address served. Mizzey adds a signup verifier: a signed,
single-use, route-bound token issued with each account-creating page, a minimum age, and a trap field. It is enforced
early on the Store API checkout and before account insertion on every WooCommerce and WordPress registration route.
Sessions stay WordPress's, documented and verified. The security check gains the rows.

## Design

| Piece | Responsibility |
|---|---|
| `src/Security/Cli/SecurityCommand.php` | `sign-in-baseline` (FR-001): reads `LoginProtectionSettingsStore::current()`, maps the settings object's camelCase properties to the store's snake_case input keys, changes the five fields, saves through `save()`, reads back in the same call and verifies every field, the untouched ones included |
| `src/Security/SignInMessages.php` | `corex_login_locked` keeps its code and gets Mizzey's translated message |
| `src/Security/SignupCheck.php` | The verifier (FR-005). Token: `v1.<base64url(json{p:"mizzey-signup",r:<route>,t:<int>,n:<16 random bytes hex>})>.<base64url(hmac)>`, HMAC-SHA256 over the payload part keyed by `wp_salt('nonce')`, compared with `hash_equals`. Input bounded to 512 bytes, strings only, strict base64 and JSON decoding, every field validated. Rejects a future timestamp, an age under 3 or over 7,200 seconds, another route, a spent nonce, or a filled trap. After the token validates, its nonce is claimed atomically in the database before insertion is authorised: `INSERT IGNORE` of an options row `mizzey_signup_claim_<n>` (non-autoloaded, value = the claim's expiry), accepted only when exactly one row was inserted. An existing claim or a storage failure refuses. Claims are never read through the object cache, are kept for the token's whole validity (expiry = issue time + 7,200 seconds + 60), are not released when a later registration step fails (a retry needs a fresh token), and expired claims are removed in bounded batches (at most 50 per claim). Routes are semantic ids: `account`, `checkout`, `order-received`, `wordpress`; language and localised paths are not part of them |
| `src/Security/SignupRoutes.php` | Route adapters (FR-003, FR-004). **Checkout**: at `rest_request_before_callbacks`, for the matched handler of POST `/wc/store/v1/checkout`, preserve an earlier response or error; when WooCommerce would create an account (signed out; `filter_var(WC()->checkout()->is_registration_enabled(), FILTER_VALIDATE_BOOLEAN)`; and either `filter_var(WC()->checkout()->is_registration_required(), FILTER_VALIDATE_BOOLEAN)` or `filter_var($request['create_account'], FILTER_VALIDATE_BOOLEAN)`, through WooCommerce's filtered checkout APIs, never the raw options), verify `extensions['mizzey-signup']` and return a 400 `WP_Error` on failure, before the callback creates or updates the draft order. REST adapter state is scoped to the exact request object: every matched request pushes its own frame, a neutral one for unrelated routes, so a nested request cannot inherit a parent's checkout permit; only the matching frame is popped at `rest_request_after_callbacks`, and no permit outlives an exceptional exit. **Account page**: within WooCommerce's registration processing (`woocommerce_process_registration_errors`, reached only after its own `woocommerce-register-nonce` or `_wpnonce` check), verify route `account` from the POST fields. **Order-received**: WooCommerce processes the offer while rendering the `woocommerce/order-confirmation-create-account` block (`render_content()` calls `process_form_post()`, which checks its `wc_create_account` nonce, the order's customer and email before `wc_create_new_customer()`). Through `register_block_type_args`, the adapter wraps only that block type's render callback: it enters an adapter context immediately before calling the original callback with unchanged arguments and restores the previous context in `finally`, so nested callbacks restore their parent's. The guard verifies route `order-received` from the POST fields only inside that context. A missing or changed callback makes `signup_check` say review rather than opening a broad exemption. **WordPress**: `registration_errors`, route `wordpress`. **Guard**: at `woocommerce_registration_errors`, an insertion requires an unconsumed permit for the current handler operation and the expected normalised email, or the WP-CLI or authorised-staff exception (`create_customers` for WooCommerce, `create_users`). A successful token claim creates one permit; the guard consumes it before allowing the intended insertion, so a second insertion or another email cannot reuse it. Unused permits are cleared when their handler operation ends, failures and short-circuits included. Anything else fails closed with the translated message |
| Rendering | Account page and WordPress registration: hidden token and trap fields printed on `woocommerce_register_form` and `register_form`. Block checkout: `assets/signup-check.js`, depending on `wp-data` and `wc-blocks-checkout`, enqueued on the checkout page only, calls `wp.data.dispatch('wc/store/checkout').setExtensionData('mizzey-signup', { token, trap })` after the store initialises and mirrors the trap input. The schema is registered with `woocommerce_store_api_register_endpoint_data()` for `CheckoutSchema::IDENTIFIER`, namespace `mizzey-signup`, writable string properties `token` and `trap`; registration does not enforce, the early validator does. Order-received: the block's PHP output is a mount, not the form, so the render filter on `woocommerce/order-confirmation-create-account` adds escaped token data to the wrapper, and `assets/signup-check.js` inserts the token and trap into the rendered form when it mounts (observing later mounts) and before submission |
| Inventory | `SignupRoutes::writers()` lists every known public account writer with its state: account page, block checkout, order-received offer, WordPress registration (checked when enabled); classic checkout (not offered by the site's page, but its native AJAX and form handlers stay registered; reported as verified closed to account creation only because direct requests with valid native nonces are refused without creating an order, which t47 proves); stock-notification signup (inactive unless `woocommerce_customer_stock_notifications_allow_signups` and `…_create_account_on_signup` are both yes; then reported as unchecked, because its failure path silently degrades to an email-only signup) |
| `src/Security/BaselineReport.php` | FR-007: `sign_in_limit`, `signup_check`, `account_writers`, `wordpress_registration`, all in `CONTROLS`. `signup_check` self-tests the verifier with a token it signs: a fresh one fails (too new), a backdated one passes once and then fails (spent); the probe nonce is removed afterwards |
| `docs/security-baseline.md` | FR-006, FR-008: the session policy, the limit and its settings, the signup method and its limits, recovery from a lockout |

The trap field is a text input with an ordinary-looking name, hidden from people with CSS and `aria-hidden`,
`autocomplete="off"` and `tabindex="-1"`, labelled for screen readers as one to leave empty.

The token authenticates server issuance for a route and an age. Being single-use, it cannot be replayed; it proves
neither a particular visitor's page view nor human interaction (spec: "The account-creation check, and what it does not
do").

## Criterion to test map

| AC | Scenario | What it asserts |
|---|---|---|
| AC-1 | `t46-sign-in-limit` | The command changes the five fields and keeps the rest. Over HTTP on `wp-login.php` and the account page in English and Arabic: five wrong passwords then the right one is refused with the translated message; a different identity from the same address signs in; the same identity from a different trusted address is unaffected; username and email are separate buckets; case and surrounding spaces normalise to one bucket; a spoofed `X-Forwarded-For` from an untrusted connection does not change the address. With the lockout period shortened through CoreX's store before the lockout is triggered (existing lockouts keep their stored deadline), the identity signs in after it ends with protection still on. Ordinary scenarios never call `reset-login` or `releaseActiveLockouts()`: they use disposable identities and remove only their own attempt rows |
| FR-002 | `t46-sign-in-limit` (browser) | In Chromium, English and Arabic: the sign-in link from the home page, the account page and the checkout; `wp-login.php` and `/corex-login/`; WP 2FA's HTML challenge and REST challenge with a wrong code, retry and success; sign-out; lost password and the reset link. Each asserts destination, preserved query arguments, language and authentication outcome |
| AC-2 | `t47-signup-check` | Request level, for the account page and the order-received offer, and the Store API checkout: no token; malformed, array, oversized, tampered, future-dated, wrong-route and spent tokens; ages of 2 and 7,201 seconds against 3 and 7,200; a filled trap. Each creates no account and shows the translated error; native nonce failures are tested apart. Checkout failures leave no account, no new order, no payment attempt, no stock or coupon reservation, and an existing pending or failed retry order unchanged. Browser level: each route submitted through its page in English and Arabic creates the account, with the extension payload and trap verified; optional account creation and required registration succeed with a valid check and fail without it, required registration also with `create_account` omitted or false; guest checkout without account creation and signed-in checkout pass without it; the effective registration filters are exercised both ways against contrary stored options. Two tabs each succeed once. Concurrent requests with one token and different emails create at most one account; an insertion failure leaves the token spent; deleting cached values does not restore a token; a claim-storage failure creates no account or order. A verified operation cannot authorise a second insertion, another email or an unrelated nested REST request. Short-circuited block rendering, nested block callbacks and caught callback exceptions leave no authorisation behind. Direct classic-checkout requests with valid nonces create no account and no order. Native behaviour kept: an administrator and an enrolled shop manager creating a customer, WooCommerce REST customer creation with `create_customers`, authorised WordPress REST user creation, WP-CLI; unauthorised callers still refused. WordPress registration is opened for one case and closed again |
| AC-3 | `t48-sessions` | Over HTTP: the authentication and logged-in cookies are `HttpOnly`; their embedded expiry and the server session's follow `auth_cookie_expiration` (two days, fourteen with "remember me"), and a cookie whose server session has expired no longer authenticates; without "remember me" the browser cookie is session-only, with it its Expires is the authentication expiry plus twelve hours; WooCommerce's account creation requests "remember me". Sign-out rejects the old cookies while another independent session continues; after a password change, pre-change cookies are rejected and native replacement cookies are allowed. `Secure` is asserted on staging over HTTPS; on the HTTP runtime it is recorded as not applicable |
| AC-4 | `t46-sign-in-limit`, `t47-signup-check` | The check passes the four rows with the baseline; with CoreX off or default addresses hidden, `sign_in_limit` says review; with an adapter or a rendering hook removed, `signup_check` says review; with stock-notification account creation switched on, `account_writers` says review; with WordPress registration opened and its hook removed, `wordpress_registration` says review |

Settings scenarios snapshot and restore exactly what they change and run serially. The emergency `reset-login` is not
run on the shared runtime; its documented behaviour is checked against CoreX's source.

## Risks

| Risk | Mitigation |
|---|---|
| CoreX's URL filters send a WPML-prefixed sign-in link to an address it does not serve | Default addresses stay served; the browser flows in FR-002 decide. A failure there stops the baseline and raises a CoreX compatibility task |
| The block checkout or the after-purchase form changes its client API | Pinned WooCommerce 11.1.0; the browser cases prove the payload reaches the server; the request-level cases prove the server independently |
| A page cache serves a token-bearing page | Verified on staging for every token-bearing route in both languages and after back-navigation; a cached token can still be valid and unspent and skip the per-view minimum delay, or be spent and refuse the next visitor; cache bypass is verified, never assumed from expiry or single use |
| A lockout on the shared runtime blocks the suite's own sign-ins | Disposable identities; `pilot_admin` is never used for failures; only the scenario's attempt rows are removed |
| Shared proxy address on staging | Recorded; the trusted-proxy setting separates resolved client addresses, while people sharing a NAT address still share the bucket for the same identity |
| A determined script that drives a page passes the check | Recorded as the method's limit; S-2 and S-3 offered |
