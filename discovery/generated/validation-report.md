### P-012

**Question.** Does WooCommerce lack a Returned to Origin order status, and does an unrecognised carrier status currently risk being mapped to Delivered?

**The design assumed.** Woo has no such status, and the carrier integration has reported cases of mapping a returned parcel to Delivered. Section 7 row 10.

**Observed.** WooCommerce 11.1.0 ships 8 order statuses: wc-pending, wc-processing, wc-on-hold, wc-completed, wc-cancelled, wc-refunded, wc-failed, wc-checkout-draft. A returned-to-origin status: none. Bosta plugin 4.5.7 maps state codes to Woo statuses: 45 to completed, 46 to completed, 48 to cancelled, 100 to cancelled, 101 to cancelled, 104 to cancelled, 20 to processing, 999999 to processing. An unrecognised state falls back to 'processing', not completed, so the feared silent Delivered does not come from the fallback. The exposure is elsewhere: states 45 and 46 are grouped as "Finished successfully" and BOTH map to completed, while only 45 sets a delivery date. Two different terminal outcomes collapse into one Woo status. The plugin ships no legend for these codes anywhere in its source, so what 46 means cannot be established from the integration itself and must come from Bosta documentation or an account. That absence is exactly what SHIP-14 exists to fix. Driving the webhook handler with state 46 on an order that was processing left it processing, and wrote meta bosta_state_code='46', bosta_status='P-012 probe payload'. The mapping is DORMANT. In handle_status_update the call to map_bosta_state_to_wc_status is commented out, so the plugin never changes order status from a webhook: it only records meta. Nothing is silently marked Delivered today, so the expectation as written is refuted. Two consequences follow. SHIP-13, carrier status reflected on the order, is NOT delivered by this plugin as shipped, which bears on the partial leverage on US-09-04. And the dormant mapping is a trap: whoever enables it inherits 45 and 46 both becoming completed.

### P-017

**Question.** When an order is placed, is the product cost frozen onto the order line item the way the price is, or does the line read a mutable current cost?

**The design assumed.** ENT-08 records the price snapshot as native but says nothing about cost. If cost is not frozen at the point of sale, editing a product cost silently rewrites every historical margin, and ADM-27's promise of accurate history does not hold. This is the one gap that cannot be repaired later, because the cost that applied on the day is gone.

**Observed.** Cost of Goods Sold was off, enabled for the test and restored afterwards. Order 23 placed with 2 units at cost 100. Order cost at sale: 200.0. Product cost then changed to 999. Same order re-read from storage: 200.0. The order kept the cost that applied on the day. WooCommerce snapshots cost onto the order during calculate_totals, so ADM-27 accurate history holds without Mizzey adding anything, provided the feature is enabled before the first order.

### P-018

**Question.** Does WooCommerce keep a structured, queryable record of when an order entered each status, or only prose in order notes?

**The design assumed.** ADM-86 contracts an order timeline and US-18-02 classifies it native. SHIP-13 reflects carrier status onto the order. If transitions are queryable rows, dispatch and delivery times are derivable and ENT-10 needs no history. If the only per-transition record is an English sentence, a delivery-time or RTO-rate figure would have to parse prose, and the timestamps must be captured while the shipment table is being designed.

**Observed.** WooCommerce 11.1.0. After pending to processing to on-hold to completed, the order carries: date_created=2026-09-09T09:49:27+00:00, date_modified=2026-09-09T09:49:29+00:00, date_paid=2026-09-09T09:49:29+00:00, date_completed=2026-09-09T09:49:29+00:00. Example: "Order status changed from On hold to Completed." The only per-transition record is an English sentence in an order note, timestamped but not structured. date_paid and date_completed are the only queryable milestones, and neither is dispatch or delivery. A delivery-time or RTO-rate figure would have to parse note prose, which is not a foundation for a reported number. US-18-02 native is right for displaying a timeline and wrong for measuring one.

### P-019

**Question.** When the same product sells in both languages, does the WooCommerce Analytics product report count it once, and does the WooCommerce Multilingual merge survive ordering and pagination?

**The design assumed.** Section 7 row 17 puts multilingual product and content at Plugin: a translation plugin and Arabic content, with no Mizzey build behind it. E24 reporting is classified partial, meaning WooCommerce Analytics supplies the base and Mizzey adds date filtering, export and role scoping on top. Neither claim says anything about what the other does to it, so the standing assumption is that a product-level report reports a product. RPT-03 best sellers and RPT-10 stock name one product once, whichever language it was bought in.

**Observed.** WooCommerce 11.1.0, WPML 4.9.7, WooCommerce Multilingual 5.5.7. Active languages: ar, en. Current language: en. Seeded English product 58 sold 3, its Arabic translation 59 sold 5, and single-language control 60 sold 6. The pair totals 8, so aggregated it is the best seller and split neither half beats the control. wc_order_product_lookup holds 2 row(s) for the pair (58=3, 59=5), so the split is real at the storage layer. Report unmerged, one page of 100, ordered by units sold: P-019 control product=6, P-019 probe product=5, P-019 probe product=3. The same page through the WCML merge: P-019 control product=6, P-019 probe product=8, reported total 2. After the merge the pair occupies 1 row(s) carrying 8 unit(s), at position 2 of 2, and the row at position 1 carries 6 unit(s). Totals recovered. Ranking did not survive, because the ORDER BY ran in SQL before the merge ran in PHP. Page 1 at 2 per page, merged the same way: P-019 control product=6, P-019 probe product=5. The English original is on page 2, so the Arabic half never finds it and is relabelled with the original title and left at its own number: "P-019 probe product" showing 5 unit(s) instead of 8. The figure is wrong and looks legitimate. A paginated product report presents a wrong number under the right product name. The merge is applied after the SQL has already ordered and cut the result set, so it can only join rows that happen to land on the same page, and it fires only on wc-analytics REST requests, which means any query Mizzey writes against the lookup tables gets none of it. RPT-03 and RPT-10 cannot be built on this base as it stands. The correction belongs in SQL: resolve product_id to its translation group before ordering and paginating, by joining icl_translations and grouping on trid. Unlike the cost field in RPT-11, nothing is lost by deciding this later: icl_translations carries the language mapping whenever the order was placed, so historical figures recompute.

### P-020

**Question.** In a low stock or out of stock list, does a product that exists in two languages appear once, twice, or only in the language the operator is viewing?

**The design assumed.** RPT-10 contracts low stock, out of stock, dead stock and adjustments as one report, and US-24-04 is classified partial on the assumption that the WooCommerce stock report supplies a sound base. The standing assumption is that the report lists the store's stock: one line per physical item, and every item that is low appears.

**Observed.** WooCommerce 11.1.0, WPML 4.9.7, WooCommerce Multilingual 5.5.7. Active languages: ar, en. Site low stock threshold: 2. Seeded: translated pair 68 (en) and 69 (ar), Arabic-only product 70 (WPML reports its language as 'ar'), and English-only control 71. All four carry managed stock of 1 against a low stock amount of 5, so every one of them is low. wc_product_meta_lookup holds 2 stock row(s) for the pair (68='1', 69='1'). The same physical item is stored as two stockable products. GET /wc-analytics/reports/stock?type=lowstock in English returned 4 row(s) in total and named: pair-en, pair-ar, arabic-only, control. In Arabic it returned 4 row(s) and named: pair-en, pair-ar, arabic-only, control. The two language views are identical, so no language scoping ran on this query in this dispatch path. That bounds what follows: the double count below is proved for the query as the controller builds it, and the opposite fault, a language-scoped list that omits an untranslated product, is not ruled out for a browser admin request. WCML removes the All languages option from the analytics switcher in classes/Reports/Hooks.php, which implies the admin is normally scoped, so the browser case is worth one manual check before US-24-04 is accepted. One physical item is listed twice, once per language, each showing the full quantity. A stock report that double counts is not a basis for a purchasing decision, and the duplicate is not marked as one. Note that both faults share one root, proved above: WCML copies the stock onto the translation, so two stockable products describe one physical item. Whether the report then shows both of them or only the one matching the current language, it is wrong, and the difference is only in which way. The correction is the same shape as P-019: resolve the product to its translation group before the list is built, by joining icl_translations and grouping on trid, so one physical item is one row whatever language the operator is in.

- **P-009.** Does WooCommerce's native stock validation and decrement hold under concurrent checkout, so that concurrent purchases of the last unit of stock result in one sale and not two? Observed: WooCommerce 11.1.0. wc_update_product_stock delegates to the data store: yes. The product data store issues arithmetic SQL for stock changes (meta_value +/- operand): yes. Two sequential decreases of 1 from a stock of 1 left the quantity at -1, so the write itself does not refuse to go negative. What it establishes is the mechanism: an arithmetic SQL write is atomic per statement, but validation and decrement are separate steps, so a gap exists in principle. Settling BR-003 needs a parallel load test against a staging site, and that should be booked rather than assumed. Section 6 calls this Native. The write is atomic, which supports that, but the check-then-write gap is real and untested, so Native is not yet earned for the concurrent case.
