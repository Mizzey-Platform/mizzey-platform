## Risks

**US-20-01, Return case queue.** WooCommerce has no return entity at all, so the queue is a Mizzey list over a Mizzey table and the waiting time column needs a case created timestamp that only exists once that table does. AC 3 also lands a pending returns panel on the Operations Console, which is TDD row 7 and sits in the previous delivery stage, so a slip in E15 blocks acceptance of this story rather than merely delaying a nice to have.

**US-20-02, Review a return case.** AC 2 requires the eligibility result and the window that was used to be shown at review time. The window is a live configuration value, so re-evaluating it when the reviewer opens the case gives a different answer after any policy change and the screen would show a window the customer was never judged against. The result and the window have to be snapshotted onto the case when the request is made, and no story states that.

**US-20-03, Decide a return.** AC 4 needs a returns decision capability that WooCommerce does not have. P-013 confirmed on 9 September that Woo contributes only the customer and shop_manager roles, so the permission this story checks arrives with the E21 role work in the previous stage and this story cannot be accepted before it. The same AC also writes to the audit log of TDD row 14, giving this one story three separate cross epic dependencies.

**US-20-04, Record receipt and condition.** AC 3 excludes disposition, so a received and inspected return never returns to sellable stock automatically. At launch every restock is a manual inventory adjustment in E17. That is contracted, RET-07 is P2, but it is an operational cost worth saying out loud at the Stage 1 walkthrough rather than discovering in week nine.

**US-20-05, Refund from the return case.** P-014 proved the Woo refund ceiling on a running install, but it proved an order level ceiling against the total paid, and AC 3 is an item level ceiling after discount apportionment. The native ceiling therefore does not satisfy AC 3 on its own and the post discount line amount is Mizzey work. P-014 also states explicitly that it did not test whether Paymob enforces the same limit gateway side, so the money movement half of AC 2 rests on analysis, not evidence.

**US-20-06, Return audit trail.** AC 3 requires a trail that cannot be edited, and TDD row 14 puts the audit log on the CoreX audit seam whose state has not been probed. P-018 confirmed that WooCommerce keeps no structured transition record of its own, only an English sentence in an order note, so nothing in this trail can rest on order notes and every one of the five recorded events has to be written deliberately by the E20 stories that raise them.

- **US-20-03.** Partial approval is per item and per quantity, and the specification does not say whether a partially approved case can be decided again on the remaining lines or is closed by the first decision. That answer changes the state machine here and the refundable amount in US-20-05.
- **US-20-03.** NOTF-07 is traced here for the decision notification, while the notification templates live in E12. Whether the 8 points include authoring the Arabic and English return decision template or only firing the event is not stated.

If the Paymob plugin does not implement process_refund, the refund becomes a manual action in the gateway with the reference keyed back in, which is a materially different story and a different acceptance conversation.
- **US-20-05.** How an order level discount is apportioned across returned lines is not defined anywhere. A partial return of a multi line order carrying an order level coupon has no stated rule, and AC 3 cannot be tested until there is one.
