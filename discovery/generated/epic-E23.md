## Risks

**US-23-01, File formats accepted.** P-008 proved the native WC_Product_CSV_Importer parses a CSV cleanly, so delimited parsing is reusable, but there is no native Excel reader and no clean refusal path, so file intake still belongs to the written engine.

**US-23-02, Encoding detection verified against Arabic.** P-008 established that Arabic product text in UTF-8 with a BOM round trips through the native import path intact, so the parsing floor holds and the remaining work is detection plus the operator prompt on top of it, not a parser of our own.

**US-23-03, Column mapping.** The contracted mapping is wider than a column to field screen: it includes source attribute to store attribute mapping and a reusable category mapping table, neither of which has a native counterpart.

**US-23-04, Saved mapping profiles.** P-008 inspected WC_Product_CSV_Importer and found no saved mapping method among its 33, so profiles are written from nothing, but they are cheap once US-23-03 exists.

**US-23-05, Preview.** Preview shares the row resolution pipeline with the US-23-06 dry run, so if the two are built independently the epic pays for the same interpretation logic twice.

**US-23-06, Dry run.** P-008 found no dry run method on the native importer, confirming section 7 row 6, and a dry run means the whole resolution pipeline must run to completion without writing, which constrains the engine design rather than adding a screen to it.

**US-23-07, Product variations.** Parent and child conversion into variable products with attributes, SKU, price and stock, plus orphan child detection, is the hardest single behaviour in the epic and is pointed at 5 against 8 for column mapping, in Stage 5 which already runs at 92 points a week, and P-008 tested a simple product only so nothing about variable products has been established.

**US-23-08, Background processing.** Action Scheduler ships with WooCommerce and provides the queue, the retry and the progress record, so this is a mechanism plus our batching rather than a runner written from nothing, but that leverage is reasoned and not probed.

**US-23-09, Safe re runs.** P-008 imported the same file twice with update_existing on and found exactly one product on SKU P008-SKU-1 afterwards, so update by SKU with no duplicate is native behaviour the engine can sit on rather than reimplement, which lowers the risk on AC-17 without removing it, because only a simple product was tested.

**US-23-10, Error report.** The row level error report shares its structure with the US-23-06 dry run report, so the two should be one generator with two entry points.

**US-23-11, Import history.** Import history records actor, action, entity and timestamp, which is the same shape as the CoreX audit seam being built for section 7 row 14, so the two should share one store rather than each growing a table; row 14 is listed for that reuse and not because this story is contracted under ADM-132 to ADM-134.

**US-23-12, Fields imported and export.** The 13 points cover six separate behaviours, of which price, stock and image sideloading have native counterparts to lean on while cost, generated alt text and export in the saved mapped format do not; the balance is defensible but this is the largest story in the epic and it sits in Stage 5.

## Open questions

- **US-23-01.** P-008 exercised a comma delimited CSV only. Tab delimited and Excel intake, and the refusal message for an unsupported file, were not probed.
- **US-23-01.** Which Excel reader is used, and whether it can stream a very large workbook rather than loading it into memory, is undecided and bears on AC 3 and on US-23-08.
- **US-23-02.** P-008 tested UTF-8 with a BOM only. Windows-1256 and UTF-16LE, which Excel and Amazon reports commonly produce for Arabic, were not tested, and neither was AC 1 automatic detection nor AC 3 asking the operator when detection is not confident. A follow up probe on those three encodings is needed before this class is safe to rely on.
- **US-23-02.** The specification states that the import specification cannot be finalised until CR-06, the real unmodified Amazon sample export, arrives. Until it does, the encoding Amazon actually produces for this seller is an assumption.
- **US-23-03.** No probe covered column mapping. The native importer does present a per run column mapping step in admin, and whether any of it is reusable rather than replaced was not established.
- **US-23-03.** Brand mapping is P1-L, so the quality bound on MIG-12 needs stating at the Stage 1 walkthrough rather than discovered at the Stage 5 gate.
- **US-23-04.** AC 2, a saved mapping applied to a file with different columns reporting the mismatch, depends on how strictly the profile records the source header set. Not probed.
- **US-23-06.** AC 3, per field overwrite control, is P1-L. Whether it is set per import run or per saved profile is not stated in the specification and should be settled with the client at the Stage 1 walkthrough.
- **US-23-07.** A probe is needed for the variable product path: parent and child rows through the import engine, and the orphan child error case. It should run against the CR-06 sample, since the Amazon parent and child shape is the thing being converted and it has not been seen yet.
- **US-23-07.** Whether re pointing this story can be absorbed inside Stage 5 or needs one of the two contingency weeks at sprints 12 and 13.
- **US-23-08.** Not probed: whether Action Scheduler holds up for a very large import on the client hosting, and whether an interrupted run can resume from a row offset rather than only being re run under US-23-09.
- **US-23-08.** AC 1, does not fail on large files, has no number attached to it. The largest file the tool must survive is not stated anywhere and depends on CR-06.
- **US-23-09.** AC 2 requires the behaviour to hold for variable products and P-008 did not test that. This is the same follow up probe as US-23-07 and it is the one probe in this epic most worth running, because AC-17 is a client run acceptance gate at Stage 5.
- **US-23-09.** Matching is by SKU. What happens to a source row with an empty or a duplicated SKU, which is common in marketplace exports, is not covered by any acceptance criterion.
- **US-23-10.** AC 3, the corrected file can be re uploaded and imported, leans on the safe re run semantics proved for simple products in P-008 and inherits the untested variable product case.
- **US-23-11.** Whether the audit seam at row 14 is available by Stage 5 sprint 12, since building import history first and migrating it onto the seam later would be paid for twice.
- **US-23-12.** AC 1 imports cost. A native product cost field on products and variations is not established, and there is an open probe question on exactly that from the margin work in E16. If cost needs a custom field then importing it is more than a column mapping and this story is under pointed.
- **US-23-12.** AC 3 imports SEO fields where present. Which SEO plugin owns those fields is not decided in the register or the Technical Design, so the target of the mapping is unknown.
- **US-23-12.** AC 4 downloads images subject to the rights confirmation at CR-08, which has not been received. The import cannot be signed off against a real catalogue until it is.
- **US-23-12.** Image download volume is the likeliest cause of a timeout in a large run and it interacts with US-23-08. No probe covers it.
