## Risks

**US-13-01, Request a return.** No probe touches Technical Design row 5 at all, so the claim that WooCommerce has no returns workflow is still analysis rather than evidence, and this is the story that has to create the return entity the customer writes to; the optional photograph upload is a customer facing file write with no constraint stated in the acceptance criteria.

**US-13-02, Return eligibility.** OD-08, the return window and any product type exceptions, is recorded in the specification as blocking the returns build and is still open, so this story cannot start even though its own logic is small and explicitly bounded away from a rule engine.

**US-13-03, Return status visibility.** P-018 refuted the assumption that WooCommerce keeps a structured, queryable status history and found only English prose in order notes, so nothing native can be reused here and the return has to carry its own state; 3 points holds only if the customer is shown the current state and the rejection reason, and is low if a dated stage by stage timeline is expected.

**US-13-04, Refund visibility.** Reclassed from the epic level custom to extend: P-014 confirmed on WooCommerce 11.1.0 that the refund record, its amount and the ceiling at the amount actually paid are native for both full and partial refunds, so what is built here is the presentation of a native record on the custom return object and the settlement timing wording, not the refund itself; if the epic points were derived with a custom factor of 1.5 to 1.7 this story should not carry it.
