## Risks

**US-08-01, Payment abstraction layer.** Claimed native and it is close to right, which is unusual in this set. WooCommerce's WC_Payment_Gateway is genuinely an internal payment interface: checkout talks to the gateway API and not to the provider, which is AC 1, and swapping provider means writing a new gateway class rather than touching checkout, which is AC 3. Extend rather than native because AC 2 asks for retries, logging and webhook handling inside the adapter and AC 4 asks for failures logged with enough detail to diagnose, none of which the base class provides. No section 7 row names payment abstraction, correctly, because the abstraction is not the gap.

**US-08-03, Callback verification.** Claimed native and that is wrong in a way worth stating plainly. WooCommerce core verifies nothing about a payment callback: signature verification is per gateway, implemented inside whichever adapter is written, so for Paymob it is Mizzey code. AC 1 is the security boundary of the whole payment flow, since without it anyone who can reach the callback URL can mark an order paid. Classified build with NO gap row, and that is the finding: section 7 has twenty rows and none of them covers callback authenticity. Row 12 is adjacent but it is about idempotency, that the same genuine callback twice is harmless, which is a different property from a forged callback being rejected. Section 7 missed this.

**US-08-06, Refunds.** P-014 proved the core of it native: a 30 partial refund against a 100 order was accepted, a further 200 against 70 remaining was rejected as an invalid refund amount, and the cumulative ceiling held. So AC 1, AC 2 and the order level part of AC 3 are WooCommerce. Extend, not native, because three criteria sit outside it: AC 4 permission gating needs the roles at section 7 row 15, AC 5 the audit log at row 14, and AC 6 the analytics event. P-014 tested the Woo bookkeeping ceiling only and explicitly not whether Paymob enforces the same limit gateway side.

## Open questions

- **US-08-01.** AC 2 names retries. What is retried, and against what, is not stated: a failed capture must not be retried blindly or it becomes the duplicate charge that PAY-05 exists to prevent. The retry policy and the idempotency work in US-07-07 have to be designed together.
- **US-08-01.** INT-16 is in the trace and was not read here. Whether it names a second provider, which would make AC 3 testable rather than aspirational, should be checked.
- **US-08-03.** Section 7 has no row for callback verification. Recorded here per the rule that a build with no gap row means section 7 missed it. The Technical Design is already with the client, so this is a correction to make in the next revision rather than a silent one.
- **US-08-03.** Flagged under at 2 points. HMAC verification alone is small, but AC 3 requires verification failures to be visible to the team rather than only in a log file, which needs a surface that does not exist. That surface is plausibly the operations console at section 7 row 7, built in E15 in sprint 9, and this story is sprint 11, so the dependency runs the right way but nobody has stated it.
- **US-08-03.** Paymob's HMAC scheme, which fields are signed and in what order, is an external input nobody has captured. Worth requesting alongside the Bosta legend at issue #234 so the two vendor documentation gaps are chased together.
- **US-08-06.** AC 3 says a refund cannot exceed what was actually paid for that ITEM after discount. P-014 tested the order level ceiling. Item level after discount needs a discount apportionment rule across returned lines, and no document states one. E20 reached the same conclusion independently from the returns side, which makes it a real gap rather than one reader's doubt.
- **US-08-06.** Whether Paymob enforces or reports its own refund limits and timing is untested and is an input to both this story and US-13-04. One probe against the Paymob sandbox would settle both.
- **US-08-06.** AC 4 and AC 5 depend on roles and the audit seam. This story is sprint 11 in Stage 4, which already runs at 68 points a week, so a slip in either dependency lands in the worst place.
