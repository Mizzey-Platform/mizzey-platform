## Risks

**US-15-01, The Operations Console.** The console has no native equivalent and no CoreX contribution: P-005 confirms corex-kit-woo is inactive scaffolding that registers nothing, so section 7 row 7 is written from zero. Acceptance criterion 4, role aware rendering, cannot be met from the Woo capability model, since P-013 confirms only shop_manager and customer exist and report access is a single all or nothing capability, so this story cannot be accepted before the six roles of gap row 15 exist.

**US-15-02, Orders requiring action queue.** The queue itself is section 7 row 7 and has no native equivalent. Acceptance criterion 4 is blocked on gap row 10: P-012 confirms WooCommerce ships eight order statuses and none of them is returned to origin, so an RTO order cannot enter this queue until the two custom statuses are registered. P-012 also found the Bosta 4.5.7 state mapping commented out in handle_status_update, so carrier driven queue entry does not happen at all today.

**US-15-03, Stock requiring attention.** P-020 refutes the assumption that the native low stock list is a sound base: with WPML active one physical item is stored as two stockable products and the analytics stock query returned the translated pair twice, each showing the full quantity, with no language scoping in that dispatch path. This panel must resolve products to their translation group by joining icl_translations and grouping on trid before the list is built, which is the same correction P-019 and P-020 put on E24. Three points does not cover that plus the missing image and unpublished lists, which have no native report at all.

**US-15-04, Today summary.** The four figure summary is part of section 7 row 7. Acceptance criterion 3 depends on gap row 11, cash on delivery collected and remitted tracked separately, which is itself a build with no probe behind it, so a revenue figure that presents collected as received is the failure mode to watch.

**US-15-05, Saved views.** Saved filtered views for admin lists have no native equivalent in WordPress or WooCommerce and sit inside section 7 row 7. Small and self contained, and the only real work is acceptance criterion 3, a saved filter that has become invalid explaining itself rather than erroring.

**US-15-06, Add a product in under three minutes.** Claimed custom, but this is the Woo product editor plus the native duplicate action, with the work being field trimming, defaults and screen layout rather than a new screen. Five points looks high for that. The flag is contingent on the probe named in open, and acceptance criterion 2 puts the measurement with the client team at the Stage 4 gate, so the risk is a timing failure in their hands, not a build failure.

**US-15-07, Inline edit grid.** Woo Quick Edit is one product at a time and there is no multi row grid that saves as a set, so this is section 7 row 7 with nothing underneath it. Acceptance criterion 3 is not row 7 work at all: the price and stock change history is the audit log at gap row 14, on the CoreX audit seam, so this story cannot be accepted before that seam is written.

**US-15-08, Bulk order operations.** Bulk status change has a crude native base, but per order rejection of invalid transitions, bulk carrier dispatch with batched airway bills, bulk packing slips and a retry safe partial failure report have no base at all. Five points against the eight on US-15-09 looks light for that spread, and two of the four criteria depend on components nobody has tested.

**US-15-09, Bulk product operations.** Claimed custom, but the WordPress and Woo bulk edit screen already carries price change by amount or percentage, stock set and adjust, status change and category assignment. The genuine gaps are the archived state, and acceptance criterion 5, one audit log entry per bulk action with its affected set, which is gap row 14. Eight points prices this as a new screen when most of it is a wrapper over an existing one. The flag is contingent on the probe named in open.

**US-15-10, Find anything quickly.** Admin order search already covers order number, name, email and billing phone, and product admin search already covers SKU, so this is an extension rather than a build: barcode search, the carrier filter and the acceptance of speed are what is left. P-007 is deliberately not cited, since it tested the storefront LIKE query in Arabic and says nothing about admin search. The real exposure is acceptance criterion 4, because meta based admin search degrades on a large catalogue and the client sets the bar at the Stage 4 gate.

**US-15-11, Admin language and mobile use.** The English admin is configuration rather than build, and the Arabic administrator guide and training session are a handover deliverable, HND-03, not code. What is real is acceptance criterion 2, mobile use of the console for order checks and stock updates, which has to be designed into the row 7 screens rather than retrofitted, and section 7 row 7 does not mention mobile at all.

## Open questions

- **US-15-01.** Which of the six ROLE-03 to ROLE-09 roles sees which console panel is specified nowhere. The console needs a panel by capability map, and that map is an input from Mustafa or the Stage 1 walkthrough, not a build decision.
- **US-15-01.** Sequencing: gap row 15 sits in E21 and this story is sprint 9. If the roles land after sprint 9 the console ships role blind and acceptance criterion 4 is deferred.
- **US-15-02.** The queue names new, unpaid, ready to dispatch and failed delivery. Only new and unpaid map to shipped Woo statuses. Whether ready to dispatch and failed delivery are two of the statuses gap row 10 registers, or are queue filters over meta, is unresolved and changes the size of this story.
- **US-15-02.** Bosta state code 46 has no legend in the plugin source, raised as mizzey-platform#234. Until it is known, which carrier states put an order into this queue for a decision cannot be settled.
- **US-15-03.** Confirm the trid grouping correction is written once as a shared resolver and used by both this panel and the E24 stock report, so it is not built twice or, worse, built in one place only.
- **US-15-03.** P-020 did not rule out the opposite fault for a browser admin request, where a language scoped list silently omits an Arabic only product. One manual check in the admin is needed before this panel is accepted.
- **US-15-03.** Lane two, recorded and not opened as a story: flagging products missing an Arabic translation in this same panel is desirable and has no Annex A id. ADM-142 lists low stock, out of stock, missing image and unpublished only.
- **US-15-04.** Acceptance criterion 2 says revenue is consistent with the sales report, but does not name which report or which basis. Net or gross, and whether uncollected cash on delivery is included, has to be fixed before the figure can be tested. Raise at the Stage 1 walkthrough.
- **US-15-04.** No probe has tested that a console figure and the WooCommerce Analytics revenue figure agree for the same period. Worth one probe before Stage 4.
- **US-15-06.** Probe request: confirm on the running install that the native product duplicate action is present in WooCommerce 11.1.0, and that a simple product publishes with title, price, stock, image and category and no other required field. The over flag rests on both being true.
- **US-15-06.** Freeing points from sprint 9 only helps if the re point is fed back into the Stage 4 plan, which already runs at 68 points a week.
- **US-15-07.** Sequencing: gap row 14, the audit log, is E19 and E21 work and this story is sprint 9. Whether the audit seam is available by then is a scheduling question for Mustafa. If it is not, acceptance criterion 3 is what slips.
- **US-15-07.** Acceptance criterion 2 says changes are saved together and failures listed individually. Whether a partial save is acceptable, or the whole set must roll back, is not stated and decides the transaction design. Raise at the Stage 1 walkthrough.
- **US-15-08.** Does Bosta WooCommerce 4.5.7 expose a bulk dispatch and a batched airway bill call, or must the build loop the single order API and handle rate limiting? P-012 established the plugin version on the runtime but not this. Probe request.
- **US-15-08.** Bulk packing slip printing, ADM-156, has no candidate named anywhere and no need row in plugins.json. If it becomes a plugin it needs a PL row with licence and annual cost, reconciled against the 107 USD already quoted to the client in Technical Design section 11.
- **US-15-09.** Probe request: on the running install, confirm the native bulk edit performs a percentage price change, a stock adjustment and a category assignment across a selection. If any of the three is absent the over flag is wrong and this row goes back to build at eight points.
- **US-15-09.** Same audit log sequencing question as US-15-07: acceptance criterion 5 depends on gap row 14 existing by sprint 9.
- **US-15-10.** Probe request: confirm on the running install that order search by customer phone works under the current order storage, that product search reaches SKU and barcode, and time both against a catalogue of realistic size. Acceptance criterion 4 has no numeric target, so the timing figure is the only defence at the gate.
- **US-15-10.** Barcode is a product field but no requirement states whether admin search must match it exactly or partially. Raise at the Stage 1 walkthrough.
- **US-15-11.** With WPML active for the storefront, confirm the admin locale stays English per user profile and that the language switcher does not change admin chrome. Probe request, small.
- **US-15-11.** Acceptance criterion 2 names order status checks and stock updates only. Which console panels must work on a phone, and which may be desktop only, needs stating before the wireframes are drawn.
