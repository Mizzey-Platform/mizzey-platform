# CoreX v0.42.0 to v0.47.0: migration readiness assessment

**Date:** 21 October 2026
**Status:** Assessment only. **Nothing is upgraded.** `corex.lock` and `stack.lock.json` stay at v0.42.0 until a
separate upgrade PR, approved by the owner, changes them. Under D-14 that PR waits for the owner to lift the
design-first restriction for this infrastructure change.
**Decision record:** ADR-0003 and D-18. Ownership findings: `docs/2026-10-21-corex-mizzey-ownership-audit.md`.

## 1. What Mizzey depends on

Mizzey's plugin and theme call no CoreX class, function or filter. What an upgrade can change is what the eight
active CoreX plugins do on the site: the page head, options, the schema, CoreX's own mail, roles, and the CLI used
to migrate. That narrows the regression surface, and it is why the tests below are mostly runtime checks rather
than code changes.

## 3. What Mizzey can reuse directly

- The CoreX inbox (`NotificationService`, category `operations`) for contracted operational conditions, through a
  thin adapter. The API is byte-identical from v0.42.0 to v0.47.0, so this does not wait for the upgrade.
- CoreX's standalone refusal page, which the accepted 09-A frames already show.
- CoreX Jobs for a staff-started resync.
- Native WordPress, WooCommerce and WPML for the logo, tokens, navigation, footer, emails, SEO output, hreflang,
  structured data and roles (audit, section 1).

## 4. Adapters that may be needed

## 5. Duplicates to disable or consolidate

The Bosta stock writers, the two coming-soon mechanisms, the CoreX patterns beside the curated library, the two
email logos and the two sender identities, and the choice of a single staff log. Each is listed with its resolution
and owner in the audit, section 2.

## 6. Database and schema risks

- **No down-migrations exist.** Reverting `corex.lock` restores files only. CoreX's own release history says that
  going back does not undo a release's database changes.
- The 0.47.0 schema change is additive and nullable, so v0.42.0 code should keep working on a version 4 table after
  a file revert. That is reasoning from the source, not a test: the upgrade PR must try it on staging.
- The retention sweep's permanent deletions cannot be undone by any revert. Only a backup restores them.
- The schema heals itself on the first admin or cron request. On staging and production that means the backup is
  taken **before** the first request to the new code, not after.

## 8. Regression tests the upgrade PR must run

Following `docs/stack-and-upgrades.md`, one component in its own PR:

1. Read the changelog of every skipped release (done for this assessment; re-read anything added after it).
2. Snapshot the disposable runtime: database dump, `corex_%` options with autoload, active plugins, the schema
   version option.
3. Edit `corex.lock` to `v0.47.0` and `3a54765`; `node tools/corex-sync.mjs`; `node tools/corex-sync.mjs --check`.
4. `wp corex migrate --dry-run`, then `wp corex migrate`, before opening wp-admin.
5. The #201 reproduction on a `--no-dev` build.
6. Discovery gate and tests, tool tests, the Pest and integration suites, `php -l`.
7. Probes P-006, P-012, P-016, P-017, P-019, P-020 against the disposable runtime only.
8. A bilingual storefront pass, English and Arabic right to left: product, cart, checkout, and the page head.
9. Capture a WooCommerce order email and a CoreX email with corex-email active.
10. HPOS compatibility screen, with `corex-kit-woo` inactive.
11. A file revert to v0.42.0 on the version 4 schema, then forward again.
12. Record the new version, status and date in `stack.lock.json`, and any behaviour change in `DECISIONS.md`.

## 9. Rollback and restore

The rollback is a **restore**, not a revert: the database dump from step 2 plus the previous `corex.lock`. The
restore is rehearsed on the disposable runtime and on staging (`mizzey-site/tests/staging/staging.py` backs up and
restores) before the upgrade is offered for merge. A production upgrade, when one exists, follows staging and needs
its own backup taken before the first request to the new code.

## 10. Still uncertain until a runtime test

The autoload state of Mizzey's `corex_*` options; `gd` and `mbstring` on every host; the schema self-heal on
staging and v0.42.0 on a version 4 table; WooCommerce mail with corex-email active; the HPOS listing; the generator
tag behind a cache; CoreX patterns in Mizzey's inserter; MariaDB 11.4 on the staging server, which is still
untested for Mizzey (D-16).

## 11. Interface requirements for the CoreX revamp

To be considered in the separate CoreX revamp backlog, not implemented for Mizzey:

- A documented way for a client site to register notification categories, abilities and activity areas.
- A notification publish call that never throws, and a resolve that respects visibility.
- One logo resolution shared by the login screen and every CoreX mail, able to follow the site's Site Logo.
- A documented token contract for CoreX blocks, and a client opt-out for CoreX patterns.
- A redirect and missing-page capability, if it is to be a framework feature.
- Down-migrations, or at least a documented restore procedure, for every schema change.
- A stated stability level for each public class and hook, so a client knows which seams survive a major version.

Speculative compatibility with any of these is not implemented. Mizzey maps them when a revamped release
publishes them.
